# Архитектура Mini Monitoring

Документ для тех, кто будет читать код: что из чего состоит, как связано и **почему**
сделано именно так. Кратко и без лишних слоёв.

## Назначение и границы

Приложение следит за доступностью сервисов, которые вы указали:

- **HTTP** — сайт или API отвечает нужным кодом;
- **TCP** — хост принимает соединение на порту;
- **процесс** — на этой машине запущен процесс с указанным именем.

Работает локально на одном компьютере, слушает `127.0.0.1`. Данные — в PostgreSQL.

## Общая схема

```text
        ┌───────────────┐
        │   Браузер     │  дашборд (HTML + JS), формы
        └───────┬───────┘
                │ HTTP
        ┌───────▼────────────────────────────────────┐
        │ FastAPI (app/main.py)                      │
        │  middleware: Host, CSRF-cookie, заголовки  │
        │  app/pages.py   — HTML-страницы            │
        │  app/api.py     — JSON API                 │
        │  app/auth.py    — вход по паролю           │
        └───────┬─────────────────────┬──────────────┘
                │                     │
    ┌───────────▼─────────┐   ┌───────▼──────────────┐
    │ app/checks/         │   │ app/scheduler.py     │
    │ http / tcp / process│◄──│ фоновый поток        │
    └─────────────────────┘   └───────┬──────────────┘
                                      │
                        ┌─────────────▼─────────────┐
                        │ app/db.py + app/models.py │
                        │ SQLAlchemy                │
                        └─────────────┬─────────────┘
                                      │
                              ┌───────▼────────┐
                              │  PostgreSQL    │
                              └────────────────┘
```

## Слои и их ответственность

| Модуль | Отвечает за | Не отвечает за |
|---|---|---|
| `app/main.py` | сборка приложения, middleware, обработчики ошибок, `/health`, запуск планировщика | бизнес-логику проверок |
| `app/pages.py` | HTML-страницы: дашборд, цель, формы | формат JSON API |
| `app/api.py` | JSON API `/api/targets`, `/api/status` | HTML |
| `app/auth.py` | вход и выход | проверку прав на каждый запрос (это зависимости) |
| `app/schemas.py` | валидация входных данных и нормализация `config` | сохранение в БД |
| `app/checks/*` | одна проверка: HTTP, TCP или процесс | хранение результатов |
| `app/scheduler.py` | когда проверять и как сохранять | как именно проверять |
| `app/models.py` | структура таблиц | логику |
| `app/db.py` | подключение, сессии, `Base` | запросы |
| `app/config.py` | настройки из `.env` | секреты в коде |
| `app/messages.py` | переводы ошибок валидации | валидацию |
| `app/security.py` | Host, CSRF, вход, лимит попыток | маршруты |

## Как проходит запрос

### 1. Открытие дашборда

1. `GET /` → `app/pages.py` рендерит `templates/index.html` (без данных).
2. Браузер загружает `static/app.js`, тот раз в 5 секунд запрашивает `GET /api/status`.
3. `app/api.py` собирает: цели + последнюю проверку + агрегаты за 24 часа.
4. JS рисует строки: статус, задержку, доступность, «N секунд назад».

Так сервер не рендерит таблицу — обновление бесплатное и не требует перезагрузки.

### 2. Добавление цели через форму

1. `GET /targets/new` — форма с CSRF-токеном.
2. `POST /targets/new` — форма проверяется зависимостью `verify_csrf`, затем
   `app/pages.py` собирает `config` под выбранный тип и валидирует **той же схемой**,
   что и API (`TargetCreate`).
3. Ошибка → страница с русским текстом, введённые значения сохраняются.
   Успех → `303` на страницу цели.

### 3. Фоновая проверка

1. Планировщик (поток, тик 5 с) читает **снимок** включённых целей простыми значениями.
2. Для каждой цели, у которой истёк `interval_seconds`, вызывается `run_check()`
   из `app/checks/__init__.py`.
3. Результат пишется в `check_results` отдельным `commit` — сбой одной цели не
   затрагивает остальные.
4. Раз в час удаляется история старше `RETENTION_DAYS`.

## Модель данных

```text
targets                          check_results
─────────────────────────        ─────────────────────────────
id            PK                 id              PK
name          unique             target_id       FK → targets (ON DELETE CASCADE)
type          http|tcp|process   checked_at      timestamptz
config        JSON               ok              bool
interval_seconds                 latency_ms      int NULL
timeout_seconds                  status_code     int NULL
enabled                          error           text NULL
created_at / updated_at          details         JSON NULL
                                 индекс (target_id, checked_at)
```

- `config` — JSON, потому что поля зависят от типа цели. Проверяется Pydantic-схемой
  при создании/изменении; лишние ключи запрещены.
- Время везде в UTC (`timestamptz`), отображение — в поясе браузера.
- История удаляется каскадом при удалении цели.

## Схема меняется только миграциями

`Base.metadata.create_all()` не используется. Любое изменение `models.py` → новая
миграция Alembic. Это гарантирует одинаковую схему на любой машине.

## Принятые решения и причины

| Решение | Почему |
|---|---|
| Синхронный SQLAlchemy и обычные `def`-эндпоинты | проще читать; FastAPI выполняет их в пуле потоков |
| TCP-проверка вместо ICMP-ping | работает без прав администратора и одинаково на Windows/Linux |
| Последовательные проверки в одном потоке | для 10–50 целей достаточно; таймаут у каждой есть |
| «Последняя проверка» хранится в памяти процесса | не нужен лишний запрос в БД; после перезапуска всё проверится заново |
| Один воркер (`--workers 1`) | иначе каждый воркер запустит свой планировщик и проверки удвоятся |
| CSRF: двойная отправка токена (cookie + скрытое поле) | не требует состояния на сервере, защищает от POST с чужих сайтов |
| Вход по паролю — опция (`APP_PASSWORD`) | локально можно без него; включили — интерфейс и API закрыты |
| CSP и заголовки безопасности в middleware | одна точка настройки для всех ответов |
| Пинование версий в `requirements.txt` | воспроизводимость |

## Чего здесь сознательно нет

Docker, Redis/Celery, JWT/OAuth, React, HTTPS-сертификаты, роли пользователей.
Для локального мониторинга это усложнение без пользы.

## Как добавить новый тип проверки

1. `app/checks/имя.py` — функция `check_x(config, timeout) -> CheckOutcome`.
2. `app/checks/__init__.py` — добавить тип в `CHECKERS`.
3. `app/schemas.py` — схема параметров и запись в `CHECK_CONFIGS`.
4. `app/pages.py` — поля формы и `_details()` для отображения.
5. `templates/form.html` — fieldset с полями.
6. Тесты: `tests/test_checks.py` + форма в `tests/test_forms.py`.
7. README: строка в таблице типов и описание `config`.

## Что можно улучшить дальше

- уведомления при сбоях (Telegram/email);
- графики истории;
- порог «N падений подряд = тревога»;
