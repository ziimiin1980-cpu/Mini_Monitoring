# Mini Monitoring

Простое локальное веб-приложение для мониторинга доступности сервисов: сайтов и API,
хостов в сети и локальных процессов.

## Цель проекта

Дать небольшой, понятный инструмент, который регулярно проверяет нужные адреса и сервисы
и показывает их состояние в браузере — без сложной инфраструктуры и тяжёлых систем
мониторинга. Проект рассчитан на запуск на одном компьютере (Windows) с возможностью
переноса на Linux-сервер, а также на изучение современной разработки на Python.

## Планируемые возможности

> Всё перечисленное ниже **ещё не реализовано** и описано как план развития.

- проверка доступности сайтов и API по HTTP (код ответа, время отклика);
- проверка хостов и сервисов в сети по TCP-порту;
- проверка, запущен ли нужный локальный процесс;
- хранение истории проверок в базе данных;
- веб-дашборд с текущими статусами, временем отклика и доступностью за сутки;
- добавление, изменение и отключение целей мониторинга без правки кода;
- автоматическое удаление устаревшей истории проверок.

## Технологический стек

- Python 3.13
- FastAPI (веб-API и отдача страницы дашборда)
- PostgreSQL (хранение целей и истории проверок)
- SQLAlchemy (работа с базой данных)
- Alembic (миграции схемы базы данных)
- HTML + JavaScript без фреймворков (дашборд)
- pytest (тесты)

## Текущий статус

Проект находится на **начальном этапе разработки**.

Уже работает: каркас приложения FastAPI, подключение к PostgreSQL, модели
(`targets` и `check_results`), миграции Alembic и CRUD-API для целей мониторинга
(создание, чтение, изменение, удаление с проверкой входных данных). Эндпоинт `/health`
проверяет, что сервер запущен и база данных доступна.

Ещё не реализовано: сами проверки сайтов/хостов/процессов, планировщик, веб-дашборд
и страница управления целями. Приложение пока ничего не мониторит.

## Подготовка базы данных

Нужен установленный и запущенный PostgreSQL (проект проверялся на версии 18).
База создаётся один раз:

```powershell
# 1. Создать базу данных mini_monitoring
$env:PGPASSWORD='<пароль пользователя postgres>'
& 'D:\postgresql\bin\psql.exe' -U postgres -h 127.0.0.1 -c "CREATE DATABASE mini_monitoring WITH ENCODING 'UTF8' TEMPLATE template0;"

# 2. Создать файл настроек и вписать в него реальный пароль вместо CHANGE_ME
Copy-Item .env.example .env

# 3. Применить миграции (создать таблицы)
.\.venv\Scripts\python.exe -m alembic upgrade head
```

Файл `.env` содержит пароль и в Git не попадает — в репозитории хранится только
`.env.example`.

## Установка и запуск

Все команды выполняются в PowerShell **из корня проекта** (`D:\Mini_Monitoring`).
Команды `python` и `pip` не обязаны быть в PATH — надёжнее обращаться к Python
внутри виртуального окружения напрямую.

```powershell
# 1. Создать виртуальное окружение (достаточно один раз)
py -3.13 -m venv .venv

# 2. Установить зависимости
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# 3. Запустить сервер
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

После запуска:

- <http://127.0.0.1:8000/health> — проверка работоспособности: приложение и база данных.
  Успех — `{"status":"ok","database":"ok"}` (HTTP 200), ошибка БД — HTTP 503 и
  `{"status":"error","database":"unavailable"}`;
- <http://127.0.0.1:8000/docs> — интерактивная документация API (Swagger UI).

Остановить сервер — `Ctrl+C` в окне терминала.

Альтернатива: активировать окружение и пользоваться короткими командами.

```powershell
.\.venv\Scripts\Activate.ps1     # в приглашении появится (.venv)
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
deactivate                       # выйти из окружения
```

## API

Все эндпоинты можно пробовать прямо в браузере через Swagger UI:
<http://127.0.0.1:8000/docs> (кнопка **Try it out** → **Execute**).

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Приложение и база данных живы |
| GET | `/api/targets` | Список целей |
| POST | `/api/targets` | Создать цель |
| GET | `/api/targets/{id}` | Одна цель |
| PUT | `/api/targets/{id}` | Заменить цель целиком |
| DELETE | `/api/targets/{id}` | Удалить цель |

Параметры проверки хранятся в поле `config` и зависят от типа цели:

| Тип | Поля `config` |
|---|---|
| `http` | `url` (обязательно), `method` (`GET` или `HEAD`, по умолчанию `GET`), `expected_status` (по умолчанию `200`) |
| `tcp` | `host` (обязательно), `port` (1–65535, обязательно) |
| `process` | `name` (обязательно) |

Пример создания HTTP-цели из PowerShell:

```powershell
$body = '{"name":"My site","type":"http","config":{"url":"https://example.com"}}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/targets `
    -ContentType 'application/json' -Body $body
```

Для имён с кириллицей проще пользоваться Swagger UI: в Windows PowerShell 5.1
кириллица в теле запроса через командную строку может искажаться.

Коды ответов: `200` — успех, `201` — создано, `204` — удалено,
`404` — цель не найдена, `409` — имя уже занято, `422` — некорректные данные.

Цель меняется целиком (`PUT`): нужно передать все поля, включая `name`, `type`,
`config`, `interval_seconds`, `timeout_seconds` и `enabled`.

## Тесты

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Запускать именно через `python -m pytest`, а не командой `pytest`: в этом случае
текущий каталог добавляется в пути импорта и тест находит пакет `app`.

## Работа с базой данных

Схема описана в `app/models.py`. Изменения схемы применяются только миграциями Alembic:

```powershell
# создать новую миграцию после изменения моделей
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "краткое описание"

# применить все миграции
.\.venv\Scripts\python.exe -m alembic upgrade head

# откатить последнюю миграцию
.\.venv\Scripts\python.exe -m alembic downgrade -1
```

Таблицы намеренно не создаются через `Base.metadata.create_all()`: единственный
источник правды о структуре базы — миграции.
