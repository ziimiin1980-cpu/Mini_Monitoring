# Mini Monitoring

Простое локальное веб-приложение для мониторинга доступности сервисов: сайтов и API,
хостов в сети и локальных процессов.

## Цель проекта

Дать небольшой, понятный инструмент, который регулярно проверяет нужные адреса и сервисы
и показывает их состояние в браузере — без сложной инфраструктуры и тяжёлых систем
мониторинга. Проект рассчитан на запуск на одном компьютере (Windows) с возможностью
переноса на Linux-сервер, а также на изучение современной разработки на Python.

## Планируемые возможности

> Всё перечисленное ниже **ещё не реализовано** и описано как план развития.

- проверка доступности сайтов и API по HTTP (код ответа, время отклика);
- проверка хостов и сервисов в сети по TCP-порту;
- проверка, запущен ли нужный локальный процесс;
- хранение истории проверок в базе данных;
- веб-дашборд с текущими статусами, временем отклика и доступностью за сутки;
- добавление, изменение и отключение целей мониторинга без правки кода;
- автоматическое удаление устаревшей истории проверок.

## Технологический стек

- Python 3.13
- FastAPI (веб-API и отдача страницы дашборда)
- PostgreSQL (хранение целей и истории проверок)
- SQLAlchemy (работа с базой данных)
- Alembic (миграции схемы базы данных)
- HTML + JavaScript без фреймворков (дашборд)
- pytest (тесты)

## Текущий статус

Проект находится на **начальном этапе разработки**.

Уже работает: каркас приложения FastAPI, подключение к PostgreSQL, модели
(`targets` и `check_results`), миграции Alembic, CRUD-API для целей мониторинга,
движки проверок (HTTP, TCP-порт, локальный процесс), планировщик с историей,
API статусов и **веб-дашборд**: таблица целей с автообновлением, страница цели
с историей, добавление, редактирование, включение/выключение и удаление целей
прямо в браузере.

Ещё не реализовано: уведомления о сбоях (Telegram/email), автозапуск при загрузке
Windows, графики истории.

## Подготовка базы данных

Нужен установленный и запущенный PostgreSQL (проект проверялся на версии 18).
База создаётся один раз:

```powershell
# 1. Создать базу данных mini_monitoring
$env:PGPASSWORD='<пароль пользователя postgres>'
& 'D:\postgresql\bin\psql.exe' -U postgres -h 127.0.0.1 -c "CREATE DATABASE mini_monitoring WITH ENCODING 'UTF8' TEMPLATE template0;"

# 2. Создать файл настроек и вписать в него реальный пароль вместо CHANGE_ME
Copy-Item .env.example .env

# 3. Применить миграции (создать таблицы)
.\.venv\Scripts\python.exe -m alembic upgrade head
```

Файл `.env` содержит пароль и в Git не попадает — в репозитории хранится только
`.env.example`.

## Установка и запуск

Все команды выполняются в PowerShell **из корня проекта** (`D:\Mini_Monitoring`).
Команды `python` и `pip` не обязаны быть в PATH — надёжнее обращаться к Python
внутри виртуального окружения напрямую.

```powershell
# 1. Создать виртуальное окружение (достаточно один раз)
py -3.13 -m venv .venv

# 2. Установить зависимости
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# 3. Запустить сервер
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

После запуска:

- <http://127.0.0.1:8000/> — **дашборд** с состоянием всех целей;
- <http://127.0.0.1:8000/health> — проверка работоспособности: приложение и база данных.
  Успех — `{"status":"ok","database":"ok"}` (HTTP 200), ошибка БД — HTTP 503 и
  `{"status":"error","database":"unavailable"}`;
- <http://127.0.0.1:8000/docs> — интерактивная документация API (Swagger UI).

Остановить сервер — `Ctrl+C` в окне терминала.

Альтернатива: активировать окружение и пользоваться короткими командами.

```powershell
.\.venv\Scripts\Activate.ps1     # в приглашении появится (.venv)
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
deactivate                       # выйти из окружения
```

## Дашборд

Откройте <http://127.0.0.1:8000/>:

- таблица целей: статус, задержка, доступность за 24 часа, время последней проверки;
- данные обновляются автоматически каждые 5 секунд, без перезагрузки страницы;
- кнопка «+ Добавить цель» открывает форму;
- клик по имени цели открывает её страницу: параметры, последние 50 проверок
  и кнопки «Проверить сейчас», «Изменить», «Выключить/Включить», «Удалить».

Цели можно добавлять как через браузер, так и через API (`/docs`) — используется
одна и та же проверка данных.

Формы работают обычными POST-запросами: при ошибке страница возвращается с текстом
проблемы и заполненными полями, при успехе — переадресация (`303`) на страницу цели.
Дашборд — HTML + JavaScript без фреймворков: шаблоны в `app/templates`,
стили и скрипты в `app/static`.

## API

Все эндпоинты можно пробовать прямо в браузере через Swagger UI:
<http://127.0.0.1:8000/docs> (кнопка **Try it out** → **Execute**).

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Приложение и база данных живы |
| GET | `/api/status` | Все цели с текущим состоянием: последняя проверка, доступность за 24 ч |
| GET | `/api/targets` | Список целей |
| POST | `/api/targets` | Создать цель |
| GET | `/api/targets/{id}` | Одна цель |
| PUT | `/api/targets/{id}` | Заменить цель целиком |
| DELETE | `/api/targets/{id}` | Удалить цель |
| GET | `/api/targets/{id}/history?limit=100` | История проверок цели (новые сверху) |
| POST | `/api/targets/{id}/check` | Проверить цель немедленно |

Параметры проверки хранятся в поле `config` и зависят от типа цели:

| Тип | Поля `config` |
|---|---|
| `http` | `url` (обязательно), `method` (`GET` или `HEAD`, по умолчанию `GET`), `expected_status` (по умолчанию `200`), `accept_any_status` (`false`), `user_agent` (необязательно) |
| `tcp` | `host` (обязательно), `port` (1–65535, обязательно) |
| `process` | `name` (обязательно) |

Пример создания HTTP-цели из PowerShell:

```powershell
$body = '{"name":"My site","type":"http","config":{"url":"https://example.com"}}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/targets `
    -ContentType 'application/json' -Body $body
```

Для имён с кириллицей проще пользоваться Swagger UI: в Windows PowerShell 5.1
кириллица в теле запроса через командную строку может искажаться.

Коды ответов: `200` — успех, `201` — создано, `204` — удалено,
`404` — цель не найдена, `409` — имя уже занято, `422` — некорректные данные.

`/api/status` возвращает по каждой цели:

- `last_check` — последняя проверка (`checked_at`, `ok`, `latency_ms`, `status_code`, `error`);
- `uptime_24h` — доля успешных проверок за 24 часа в процентах (`null`, если проверок ещё не было);
- `checks_24h` — сколько проверок выполнено за 24 часа.

`/api/targets/{id}/history` отдаёт последние проверки цели, самые новые первыми;
параметр `limit` — сколько записей вернуть (по умолчанию 100, максимум 1000).

Цель меняется целиком (`PUT`): нужно передать все поля, включая `name`, `type`,
`config`, `interval_seconds`, `timeout_seconds` и `enabled`.

## Как работают проверки

Каждая проверка получает параметры цели (`config`) и таймаут, а возвращает единый
результат `CheckOutcome`: успех, задержка в миллисекундах, код ответа и текст ошибки.

| Тип | Что делает |
|---|---|
| `http` | Отправляет GET/HEAD-запрос и сравнивает код ответа с ожидаемым |
| `tcp` | Пробует открыть TCP-соединение с `host:port` (успех = порт принимает подключения) |
| `process` | Ищет на этой машине процесс с указанным именем |

Проверки никогда не выбрасывают исключений: любая проблема возвращается как
неуспешный результат — так одна «плохая» цель не сможет остановить остальные.

### Если сайт отвечает 403 или 404

`403` означает «сервер работает, но нам отказывает»: защита от ботов, нужен вход
или API-ключ. `404` — «сервер работает, но такого адреса нет». Ни то, ни другое
не означает аварию.

У HTTP-цели есть два режима (в форме — поле «Что считать успехом»):

| Режим | `config` | Когда использовать |
|---|---|---|
| Конкретный код | `{"expected_status": 200}` | Нужно знать, что страница реально отдаёт нужный ответ |
| Любой ответ сервера | `{"accept_any_status": true}` | Нужно знать только, что сервер жив: 403 и 404 считаются успехом, 5xx — провалом |

Проверка отправляет браузерный `User-Agent`. Если нужен свой (например, для API),
его можно задать в `config`: `{"user_agent": "MyBot/1.0"}` (пока только через API).
Учтите: крупные сайты с сильной защитой (например, Ozon) отдают 403 даже браузерному
`User-Agent` — для них подходит режим «любой ответ сервера».

Автоматического запуска пока нет: планировщик, который будет вызывать проверки
по расписанию и сохранять результаты в `check_results`, появится на следующем шаге.

## Планировщик

Планировщик запускается вместе с приложением и работает в фоновом потоке:

- каждые 5 секунд проверяет, каким целям пора пройти проверку (у каждой свой `interval_seconds`);
- выполняет проверки по очереди, каждую — с таймаутом из `timeout_seconds`;
- сохраняет каждый результат в таблицу `check_results` (имя цели, время, успех, задержка, код ответа, текст ошибки);
- раз в час удаляет историю старше 30 дней.

Если проверка упала с ошибкой — это не исключение, а обычный результат с `ok = false`
и понятным текстом ошибки. Планировщик продолжает работать.

Важно: приложение нужно запускать с **одним процессом** (`--workers 1`, это значение
по умолчанию). Если запустить несколько воркеров, каждый создаст свой планировщик и
проверки начнут дублироваться.

Проверить результаты можно в базе:

```powershell
$env:PGPASSWORD='<пароль postgres>'
& 'D:\postgresql\bin\psql.exe' -U postgres -h 127.0.0.1 -d mini_monitoring -c `
  "select t.name, r.ok, r.latency_ms, r.error, r.checked_at from check_results r join targets t on t.id = r.target_id order by r.id desc limit 20;"
```

## Тесты

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Запускать именно через `python -m pytest`, а не командой `pytest`: в этом случае
текущий каталог добавляется в пути импорта и тест находит пакет `app`.

## Работа с базой данных

Схема описана в `app/models.py`. Изменения схемы применяются только миграциями Alembic:

```powershell
# создать новую миграцию после изменения моделей
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "краткое описание"

# применить все миграции
.\.venv\Scripts\python.exe -m alembic upgrade head

# откатить последнюю миграцию
.\.venv\Scripts\python.exe -m alembic downgrade -1
```

Таблицы намеренно не создаются через `Base.metadata.create_all()`: единственный
источник правды о структуре базы — миграции.
